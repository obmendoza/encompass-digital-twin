# NPNQM Document Requirements Checklist Ingest — Design Spec

> **Goal:** Build an operator-driven ingestion path that imports NPNQM's engine-generated `Document_Requirements_All_Income_Types.md` snapshot into queryable Postgres storage, scoped per tenant + per KB version, and produces a single `resolveRequiredDocs(loan, tenantId)` helper that downstream features (Predictive Conditions, VA Doc Review specialist) consume.

> **Architecture:** A new CLI (`scripts/ingest-doc-checklist.ts`) reads a structured markdown file with four content sections, runs four section-specific parsers, writes three new tenant-scoped tables (`program_doc_checklist`, `program_doc_engine_rules`, `income_type_resolver`), and ties the ingest to a `kb_versions` row for two-key approval per spec F2. The markdown is treated as an immutable snapshot of an upstream Python engine (`eligibility_check_v2.py`); the ingester verifies parity via the raw pipe-list digests embedded in the file.

> **Tech Stack:** TypeScript (`tsx` CLI), Node `marked` for markdown AST, Postgres with RLS, existing `@twin/api`'s `withDb` / `withTenantTx` connection helpers. No LLM calls. No PDF/Vision dependencies. Deterministic, idempotent, free.

## 1. Source Artifact

NPNQM hands us a markdown file named `Document_Requirements_All_Income_Types.md`, produced by `sync_doc_requirements_from_engine.py` against `eligibility_check_v2.py` at a known timestamp. The file is **the canonical export of NPNQM's eligibility engine** for a given release version.

### 1.1 File Structure

Throughout this spec we refer to the **source-file's** own H2 sections as **File Section A / B / C / D** to avoid collision with the spec's own numbered sections.

| File Section | Source heading | Content | Parser target table |
|---|---|---|---|
| **A** | `## 1. How to read this document` (incl. the engine-rules sub-table) | LLC closing, Field Review, US Credit rules | `program_doc_engine_rules` |
| **B** | `## 2. Document output by income scenario` | 25 income-type scenarios, each with `Minimum required documents` + `Income documentation` ordered lists + raw engine messages | `program_doc_checklist` |
| **C** | `## 3. Conditional snapshots` | Examples showing rule application (NY-Brooklyn-Investment, LLC-Investment) | informational only — not parsed; cross-checked against File Section A rules during parity verification |
| **D** | `## 4. Quick reference: Frontend → resolved Neo4j type` | Markdown table mapping UI inputs to canonical income type strings | `income_type_resolver` |

### 1.2 Invariants the ingester relies on

- Each `### <Scenario Name>` block in File Section B contains exactly the labels `**Resolved Neo4j income type**:` and `**Program (validation context)**:` followed by a backticked value.
- Each scenario has two ordered lists under headings `#### Minimum required documents (engine order)` and `#### Income documentation (engine order)`.
- Each scenario closes with a `<details><summary>Raw engine messages</summary>` block containing two backtick-quoted lines starting with `Minimum:` and `Income:`.
- File Section D's table column order is `IncomeDocType | BorrowerType | Citizenship | ITIN | Resolved` (header row exact match).
- The generation timestamp footer (`_Generated by sync_doc_requirements_from_engine.py at YYYY-MM-DD HH:MM:SS_`) is captured into the `kb_versions` row's metadata for traceability.

If any invariant breaks, the ingester aborts with a precise error before touching the database.

## 2. Data Model

> **⚠️ RLS-alone is not sufficient under the Supabase session pooler.** Every SELECT, UPDATE, and DELETE against `program_doc_checklist`, `program_doc_engine_rules`, and `income_type_resolver` MUST include an explicit `WHERE tenant_id = ...` clause in addition to RLS. The `withTenantTx` wrapper sets `SET LOCAL app.current_tenant`, but the connecting pooler role has BYPASSRLS, so the policy is unenforced from the API path. This applies to the resolver service in §4 and to any future consumer. See `feedback_supabase_pooler_bypassrls` in project memory.

### 2.1 New Tables

```sql
-- Migration 016-doc-checklist.sql

-- kb_versions.id is SERIAL INT (per migration 012); FKs use INT, not UUID.

CREATE TABLE IF NOT EXISTS program_doc_checklist (
  tenant_id            UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  kb_version_id        INT  NOT NULL REFERENCES kb_versions(id) ON DELETE CASCADE,
  resolved_income_type TEXT NOT NULL,
  program              TEXT NOT NULL,
  minimum_docs         JSONB NOT NULL,     -- [{order:int, name:str, note:str|null}]
  income_docs          JSONB NOT NULL,     -- same shape
  raw_min_msg          TEXT NOT NULL,      -- production engine pipe-list verbatim
  raw_income_msg       TEXT NOT NULL,
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, kb_version_id, resolved_income_type)
);
CREATE INDEX idx_pdc_tenant_version ON program_doc_checklist(tenant_id, kb_version_id);

CREATE TABLE IF NOT EXISTS program_doc_engine_rules (
  tenant_id     UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  kb_version_id INT  NOT NULL REFERENCES kb_versions(id) ON DELETE CASCADE,
  rule_name     TEXT NOT NULL,             -- 'llc_closing_docs' | 'field_review' | 'us_credit_optional'
  predicate     JSONB NOT NULL,            -- {LLCOrLegalEntity: true, occupancy_in: ['investment'], program_not_in: [...]}
  effect        JSONB NOT NULL,            -- {add_docs: [str], remove_docs: [str]}
  description   TEXT NOT NULL,             -- human-readable text from the engine-rules table
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, kb_version_id, rule_name)
);

CREATE TABLE IF NOT EXISTS income_type_resolver (
  tenant_id            UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  kb_version_id        INT  NOT NULL REFERENCES kb_versions(id) ON DELETE CASCADE,
  income_doc_type      TEXT NOT NULL,      -- 'Full Doc' | 'Bank Stmts: 12 Mo. Personal' | ...
  borrower_type        TEXT NOT NULL,      -- 'W2' | 'Self-Employed'
  citizenship          TEXT NOT NULL,      -- 'US Citizen' | 'Foreign Nationals'
  is_itin              BOOLEAN NOT NULL,
  resolved_income_type TEXT NOT NULL,
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, kb_version_id, income_doc_type, borrower_type, citizenship, is_itin)
);

-- RLS
ALTER TABLE program_doc_checklist        ENABLE ROW LEVEL SECURITY;
ALTER TABLE program_doc_engine_rules     ENABLE ROW LEVEL SECURITY;
ALTER TABLE income_type_resolver         ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_pdc  ON program_doc_checklist     USING (tenant_id = current_setting('app.current_tenant', true)::uuid);
CREATE POLICY tenant_isolation_pder ON program_doc_engine_rules  USING (tenant_id = current_setting('app.current_tenant', true)::uuid);
CREATE POLICY tenant_isolation_itr  ON income_type_resolver      USING (tenant_id = current_setting('app.current_tenant', true)::uuid);

-- ── Enforce single-active-version-per-tenant on the existing kb_versions
-- table (F2). This is a schema-level guard for the activation race covered
-- in §8.2. Without it, two concurrent --activate calls can leave two rows in
-- status='active' for the same tenant, making `resolveRequiredDocs(null,...)`
-- ambiguous. Migration 016 adds it; it belongs in this spec because this is
-- the first feature that depends on `WHERE status='active'` being unique.
CREATE UNIQUE INDEX IF NOT EXISTS kb_versions_one_active_per_tenant
  ON kb_versions (tenant_id)
  WHERE status = 'active';
```

### 2.2 Predicate shape for engine rules

```ts
type RulePredicate =
  | { kind: "llc_closing_docs";  LLCOrLegalEntity: true;  occupancy_in: ("investment" | "second_home")[]; program_not_in: string[] }
  | { kind: "field_review";      state: "NY";  county_in: ("Brooklyn" | "Kings")[];  occupancy_in: ("investment" | "second_home")[] }
  | { kind: "us_credit_optional"; USCredit: false };

type RuleEffect = {
  add_docs:    string[];     // verbatim doc names, inserted at engine-defined position
  remove_docs: string[];     // doc names matched literally against minimum_docs[].name
};
```

Three rules total in NPNQM's current snapshot. The parser maps the engine-rules table rows to this fixed shape; unknown rule names abort the ingest. Future engine releases that add a new rule require a small parser update (caught explicitly, not silently dropped).

### 2.3 Why the file's "Minimum required documents" is the same 9 items across all scenarios

The minimum-doc baseline is constant by design — it's the base eligibility set; per-scenario variance lives in `income_docs`. We store the minimum list per scenario anyway (not deduplicated to a base table) so that **a future engine release that splits the baseline** doesn't break the schema. Storage cost is trivial (~200 bytes × 25 rows).

### 2.4 KB-version content discriminator

`kb_versions.source_documents` JSONB carries a `kind` discriminator at the top level: `'narrative_chunks' | 'program_matrices' | 'doc_checklist'`. This is how downstream queries (e.g., "show me all active KB versions and what content they cover") distinguish content types without a dedicated column. Future versions that bundle multiple content types extend `kind` to an array. No new column on `kb_versions` is added by this spec.

The ingest CLI writes:
```jsonc
source_documents: {
  "kind": "doc_checklist",
  "source_file": "<absolute path>",
  "source_file_sha256": "<hex>",
  "generated_at": "<footer ISO timestamp>",
  "ingested_by_cli": true
}
```

## 3. Ingest CLI

### 3.1 Invocation

```bash
pnpm tsx scripts/ingest-doc-checklist.ts \
  --tenant npnqm-twin \
  --version 1 \
  --as <operator-user-uuid> \
  --file docs/npnqm-source/Document_Requirements_All_Income_Types.md \
  [--max-age 30] \
  [--dry-run]
```

| Flag | Required | Meaning |
|---|---|---|
| `--tenant <slug-or-uuid>` | yes | Target tenant. Slug or UUID accepted. |
| `--version <int>` | yes | KB version number written to `kb_versions.version` (INT per migration 012). Unique within tenant. Operator selects the next integer (1, 2, 3…); CLI rejects re-use of an existing version. |
| `--as <uuid>` | yes | Operator user id persisted as `kb_versions.ingested_by`. |
| `--file <path>` | yes | Path to the markdown file. |
| `--max-age <days>` | no | If set, the CLI parses the footer's `Generated at YYYY-MM-DD HH:MM:SS` timestamp and refuses to ingest a file older than the threshold. Surfaces stale-markdown failure modes operationally (e.g., NPNQM updated `eligibility_check_v2.py` and forgot to regenerate). Default unset (no age check). Recommended for production runbooks: `--max-age 30`. |
| `--dry-run` | no | Parse + validate; print summary; do not write to DB. |

The human-readable version string from the markdown footer (e.g., `Generated by ... at 2026-05-11 08:15:02`) is stored in `kb_versions.source_documents` JSONB for traceability — not as the version primary key.

### 3.2 Flow

```
1. Resolve tenant slug → tenant_id  (api existing GET /tenants/:slug-or-uuid)
2. Read + parse markdown:
   - 2a. Parser A: File Section B → ScenarioRow[]      (25 rows)
   - 2b. Parser B: File Section A rules sub-table → RuleRow[]  (3 rows)
   - 2c. Parser C: File Section D mapper table → ResolverRow[]  (≥32 rows)
   - 2d. Invariant checks (see §1.2)
3. Insert kb_versions row:
     status='pending_approval'   -- per the F2 status enum
     version=<arg>                -- INT, must be new
     source_documents=jsonb_build_object(
       'kind', 'doc_checklist',
       'source_file', <path>,
       'source_file_sha256', <hash>,
       'generated_at', <footer-timestamp>,
       'ingested_by_cli', true
     )
     ingested_by = <operator-user-id from env or --as>
4. withTenantTx(tenant_id):
   - Bulk insert all ScenarioRow into program_doc_checklist
   - Bulk insert all RuleRow into program_doc_engine_rules
   - Bulk insert all ResolverRow into income_type_resolver
5. Print summary: # scenarios, # rules, # resolver rows, kb_version_id, kb_version (INT), "next: pnpm tsx scripts/approve-kb.ts --version-id <id> --as admin"
6. Exit 0
```

All inserts within step 4 share a single transaction; partial-ingest is impossible.

### 3.3 Re-ingest semantics (safe but not strictly idempotent)

Each ingest creates a **new `kb_versions` row** (`pending_approval` until approved). Re-ingesting the same file produces a new pending version; the previous version (approved or not) is untouched. Operator chooses which version to activate via the separate `scripts/approve-kb.ts` step. This is consistent with how F2 handles guideline/matrix re-ingest.

The behavior is **safe but not strictly idempotent**: identical input does not produce identical DB state (a new pending row appears each run). Operators who want to dedupe can pre-check `source_documents->>'source_file_sha256'` across recent `pending_approval` rows for the tenant and skip if a match exists. Implementing strict idempotency (auto-reuse the matching pending row) is deliberately deferred — the small cost of duplicate pending rows is acceptable; the cost of silently accepting "looks like the same file" when an operator intended a fresh ingest is not.

### 3.4 Parity verification

For each ScenarioRow, the parser produces a normalized pipe-list from the parsed `minimum_docs`/`income_docs` arrays and asserts it equals `raw_min_msg` / `raw_income_msg` from the markdown's `<details>` block. Mismatches abort the ingest with a diff. This catches:
- Parser bugs (we emitted a different list than what the engine produced)
- Stale markdown (the file's parsed sections don't match its own embedded engine messages)
- Hand-edits to the file post-generation

## 4. Resolution Helper (Downstream Consumer)

A single function in `packages/api/src/services/doc-requirements.ts`:

```ts
export async function resolveRequiredDocs(
  tenantId: string,
  kbVersionId: number | null,   // null → use active version (status='active')
  loan: LoanContext,
): Promise<{ minimum: DocItem[]; income: DocItem[]; appliedRules: string[]; resolvedIncomeType: string }>;

type LoanContext = {
  incomeDocType: string;        // from loan UI fields / Encompass JSON
  borrowerType: "W2" | "Self-Employed";
  citizenship: "US Citizen" | "Foreign Nationals";
  isItin: boolean;
  llcOrLegalEntity: boolean;
  occupancy: "primary" | "second_home" | "investment";
  state: string;
  county: string;
  usCredit: boolean;
  program: string;
};
```

Implementation (pseudo):
```
1. Resolve the target kb_version_id:
   - If caller passed an explicit integer → verify it exists and belongs to tenant
   - If null → SELECT id FROM kb_versions WHERE tenant_id = $1 AND status='active'
2. Look up income_type_resolver by (incomeDocType, borrowerType, citizenship, isItin) → resolvedIncomeType
3. Look up program_doc_checklist by resolvedIncomeType → base lists
4. Fetch all engine rules for the kb_version
5. For each rule whose predicate matches the LoanContext: apply effect (add/remove docs)
6. Return the final lists + which rules fired
```

**Error semantics (binding contract for downstream callers):**

| Condition | Behavior |
|---|---|
| `kbVersionId = null` and no `kb_versions` row has `status='active'` for the tenant | Throws `NoActiveKbVersionError` (domain error, not programmer error). Callers handle by surfacing an operator-actionable message ("Tenant has no active KB version — admin must run two-key approval before document review is available") or by falling back to a conservative default checklist defined in their own spec. |
| `kbVersionId = <int>` and that version does not exist, or exists but belongs to a different tenant | Throws `KbVersionNotFoundError`. Callers surface as 404. |
| `kbVersionId = <int>` is in `pending_approval` or `pending_compliance` | Allowed — operators querying a pending version for verification can pass the explicit id. **Never** used by the `null` path. |
| `(incomeDocType, borrowerType, citizenship, isItin)` has no row in `income_type_resolver` | Throws `IncomeTypeUnresolvedError` with the four input values in the error metadata. This indicates either a loan with malformed input or a KB version that didn't seed a row for this combination (engine-coverage gap). |

A pending-but-not-yet-active version is **never** auto-selected by `resolveRequiredDocs(null, ...)`. This guarantees the resolver is deterministic against `status='active'` (which §2.1's partial unique index already enforces is at most one row per tenant).

**The function itself is in this spec's scope.** Its downstream callers (Predictive Conditions, Doc Review specialist wiring, UI display) are deliberately deferred to their own specs — this design just makes them possible.

## 5. Markdown Parser Design

Three small parsers, one per section, all in `packages/api/src/ingestion/doc-checklist-parser.ts`:

```ts
export function parseScenarios(markdown: string): ScenarioRow[];
export function parseEngineRules(markdown: string): RuleRow[];
export function parseResolverTable(markdown: string): ResolverRow[];
export function parseAll(markdown: string): {
  scenarios: ScenarioRow[];
  rules: RuleRow[];
  resolver: ResolverRow[];
  generatedAt: string;          // from footer
  sourceHash: string;           // sha256 of file content
};
```

**Approach:** parse the markdown to a `marked` AST, then walk the token tree section-by-section. Each parser:
- Scopes to its section via the H2 heading text
- Within the section, iterates expected sub-tokens (H3 / H4 / list / table)
- Throws on first invariant violation with a precise file-position-aware message

We do not use regex on raw markdown strings except for the engine-message backtick extraction (where AST-level info is less useful than the literal pipe-list).

**Why not LLM extraction:** The file is a 100% deterministic engine export with stable structure. LLM extraction would add cost, non-determinism, and a dependency we don't need. The whole point of the markdown path is that it's faster and cheaper than the PDF/Vision path.

## 6. Error Handling

Exit-code convention: **low codes for infrastructure/DB failures, high codes for input/parse failures.** Operators reading non-zero exits should treat 1-2 as "infrastructure broken — check DB/env" and 3+ as "input file or operator argument wrong — fix and retry."

| Failure mode | Exit | Behavior |
|---|---|---|
| Generic / unexpected runtime error | 1 | Stack trace, no DB writes |
| DB connection / constraint failure mid-transaction | 1 | Transaction rollback, constraint name in stderr |
| Tenant not found | 2 | Clean message, no DB writes |
| Markdown file missing or unreadable | 2 | Path echoed, no DB writes |
| Parser invariant violation (missing label, wrong table headers, etc.) | 3 | Precise file:line message, no DB writes |
| Parity check failure (parsed list ≠ raw engine message) | 4 | Print unified diff, no DB writes |
| Unknown rule name in File Section A engine-rules table | 5 | Explicit so we don't silently drop new rules; lists the unrecognized rule names |
| File age exceeds `--max-age` | 6 | Footer timestamp echoed; suggests regen upstream |
| Same-version `--version` value already exists for tenant | 7 | Lists existing version + status; operator picks the next integer |
| Same-version re-ingest *with new version int* | n/a (allowed) | New `kb_versions` row, prior one untouched; operator-controlled |

All failures are atomic at the DB layer: no partial state ever lands.

## 8. Two-Key Approval (build minimal `scripts/approve-kb.ts`)

Spec F2 designed `kb_versions` with two-key approval enforced by a `CHECK (approved_by IS NULL OR compliance_signoff_by IS NULL OR approved_by <> compliance_signoff_by)` constraint, but the actual approval workflow was never implemented (no script, no endpoint operates on `approved_by` / `compliance_signoff_by` in `packages/api/src/` today). Without an activation path, the resolver helper has no `status='active'` row to read.

This spec includes a minimal `scripts/approve-kb.ts` to close that gap. It is small (~80 lines) and belongs to this design rather than wait for an F2 completion pass.

### 8.1 CLI

```bash
pnpm tsx scripts/approve-kb.ts \
  --tenant <slug-or-uuid>          # required: defense against wrong-version cross-tenant approval
  --version-id <int>               # the kb_versions row to act on
  --as admin                        # or --as compliance_officer
  --user-id <uuid>                  # the approving user
  [--activate]                      # second-key call only: flip status to 'active'
  [--yes]                           # skip the interactive confirmation prompt (for automation)
```

| Flag | Required | Meaning |
|---|---|---|
| `--tenant <slug-or-uuid>` | yes | Defense against cross-tenant operator error: the script asserts `kb_versions.tenant_id` matches this argument's resolved tenant id before any write. Off-by-one version-ids that happen to belong to another tenant fail fast. |
| `--version-id <int>` | yes | `kb_versions.id` (global SERIAL across tenants). |
| `--as admin \| --as compliance_officer` | yes | Role being asserted. |
| `--user-id <uuid>` | yes | The approving user's id, persisted to `approved_by` or `compliance_signoff_by`. |
| `--activate` | no | Only valid with `--as compliance_officer`. Atomically flips `status='active'` and demotes any prior active row to `superseded`. |
| `--yes` | no | Skip the interactive `[y/N]` confirmation. Required for non-interactive automation. |

**Confirmation prompt (when `--yes` is absent).** Before any write the script prints:
```
Version <id> belongs to tenant <slug> (id: <uuid>).
Current status: <pending_approval | pending_compliance | active>.
Action: approve as <admin | compliance_officer> with user-id <uuid> [+ activate].
Proceed? [y/N]:
```
Operator types `y` (case-insensitive) to continue; anything else aborts with exit 0 and no DB change.

### 8.2 Behavior

| Call | DB updates | Status transition |
|---|---|---|
| `--as admin` | `approved_by = <user_id>`, `approved_at = now()` | `pending_approval` → `pending_compliance` |
| `--as compliance_officer` (no `--activate`) | `compliance_signoff_by = <user_id>`, `compliance_signoff_at = now()` | `pending_compliance` → `pending_compliance` (waits for a subsequent `--activate` call) |
| `--as compliance_officer --activate` | both signoff columns + `status='active'`, `activated_at=now()`, prior active row demoted to `superseded` with `superseded_at = now()` | `pending_compliance` → `active` |

**Activation transaction shape (R1 from review).** The `--activate` path is a single atomic transaction guarded by a row lock on the prior active row:

```sql
BEGIN;
-- 1. Lock the prior active row to serialize concurrent --activate calls.
SELECT id FROM kb_versions
 WHERE tenant_id = $1 AND status = 'active'
 FOR UPDATE;
-- 2. Demote the prior active row, if one exists.
UPDATE kb_versions
   SET status = 'superseded', superseded_at = now()
 WHERE tenant_id = $1 AND status = 'active';
-- 3. Promote the target row.
UPDATE kb_versions
   SET status = 'active',
       activated_at = now(),
       compliance_signoff_by = $2,
       compliance_signoff_at = now()
 WHERE id = $3 AND tenant_id = $1 AND status = 'pending_compliance';
-- 4. Verify row 3 affected exactly 1 row (else rollback — concurrent edit raced us).
COMMIT;
```

The partial unique index `kb_versions_one_active_per_tenant` from §2.1 is the second line of defense: if step 3 somehow promotes a row while step 2's demotion hasn't landed (impossible under the row lock above, but the index protects against future refactors), the constraint violation aborts the transaction.

**Separation of duties.** Same-user attempts (admin and compliance using identical `--user-id`) trip the `different_approvers` CHECK constraint at update time, surfaced as a clean error message (`separation-of-duties violated: user <uuid> is already the approver`). The DB enforces the rule; the script just routes the error.

### 8.3 Audit-log enforcement (fail loud, not soft)

This script's whole purpose is to perform actions that **must** be audited under SOC 2 (operator privilege exercised against credit-decision policy). The script **refuses to run** unless an audit-log writer is configured. Two acceptable shapes satisfy this:

1. A trigger on `kb_versions` that writes to `tenant_audit_log` on UPDATE (the pattern spec F2 §0.3 specifies). If present, the script trusts it and proceeds.
2. An explicit application-level INSERT into `tenant_audit_log` performed inside the same transaction as the approval write (idempotent — if the trigger also fires, the application's row is suppressed by a unique constraint on `(target_tenant_id, action, metadata->>'kb_version_id', actor_id)` — added by migration 016 alongside the new tables).

The script picks option 2 (explicit write) so it does not depend on a runtime trigger configuration check. The audit row captures: actor (`--user-id`), target tenant, action (`kb_version.approve` | `kb_version.compliance_signoff` | `kb_version.activate`), version id in metadata, prior status, new status.

If for some reason the audit-log insert fails inside the transaction, the entire approval rolls back. **No approval ever happens without a matching audit row.** That's the contract.

### 8.4 Out of scope for `approve-kb.ts`

- UI/wizard for approval (CLI only — operators run from a terminal)
- Email notifications
- Multi-tenant batch approval (one tenant, one version per invocation)

## 9. Non-Goals (Explicit)
